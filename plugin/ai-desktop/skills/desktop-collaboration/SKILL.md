---
name: desktop-collaboration
description: Coordinate an explicitly requested multi-executor writing and independent review task on AI Desktop materials from the original Codex conversation, including interruption recovery and native file writeback.
---

Keep the user's messages, progress, execution, permissions, and stopping in the original Codex conversation. The desktop shows materials and task records. Do not create a second chat interface, background executor, VM, or recurring automation.

Use this workflow only when the user requests a shared writing/review workflow or otherwise explicitly authorizes delegation. A request to develop this plugin is not a request to run a multi-executor task. Do not spawn a reviewer just because this skill is installed.

1. Use the user's current material reference and actual goal to call `desktop_task_start`. Specify only the referenced object IDs and the subset explicitly authorized for writing. Do not reuse stale references or expand access.
2. Keep the returned writer credential. Call `desktop_task_action` with `next` to obtain the current phase, pending feedback, budget, and execution instructions. After interruption inspect this state and old file sessions first; do not rerun completed work.
3. Read each material with `desktop_read_objects`. For whole native files, additionally call `desktop_prepare_file` with intent `read` using the task credential and inspect the actual source using the current conversation's file tools. Object metadata alone does not satisfy native file review. For a native selection (`selection.type=native`), read only `selectedText` and `nativeSelection` returned by `desktop_read_objects`; the writer uses `desktop_edit_file_selection` with the returned selection ID, then continues with the new selection ID from the receipt. Do not fetch the full file for a partial reference. Plain `file_text` references and PDF text selections remain read-only. The writer may prepare `edit` only for task `writeObjectIds`; a reviewer may only prepare `read` in its own host context. Read all current task sources before editing or giving feedback. Prepare an `edit` working copy and commit it through `desktop_file_result`; do not share working copies or credentials across roles. Save to the existing object; never replace it with a new object. After a commit, read the updated file before handing it off for review. Current editor leases, drafts, source versions, protected ranges, cancellation and budgets still apply.
4. After a real write, call `invite_review`. Give the returned invitation and goal to a real independent Codex executor using the host's available delegation tools. Use collaboration tools when available; do not create a user-visible chat unless the user requested a new chat. Never invent an executor, model identity, token count, or host session. If the host exposes the same session identity to both executors, report that independent review is unavailable instead of claiming it occurred.
5. The reviewer calls `desktop_task_join`, reads all current inputs, then submits `feedback` with `approve` or `revise` and concrete evidence. Reviewer credentials are read-only. The writer waits using the host's actual agent waiting facilities, then calls `next` to fetch the feedback. Do not send messages to unrelated chats.
6. On `revise`, the writer calls `acknowledge` with the real feedback ID, commits revisions, and invites another review round. On `approved`, summarize the changed objects and remaining limits in the original conversation. User confirmation of completion remains in the desktop task controls.
7. Use `progress` to retain a short progress message and actual host execution reference when available. `reportedTokens` is optional and cumulative per participant; it is explicitly executor-reported, never treated as trusted billing or a hard budget. Do not estimate it. `usageEvidence.hostTokens` remains unavailable unless the host provides authenticated task-level metering; a reported execution reference is not proof of billing. The plugin enforces commit/feedback counts and a wall-clock read/write deadline, including waiting and pauses. It cannot stop host model spending. Respect its limits and pause/cancel responses; use original-conversation execution controls to stop real processes.
8. After interruption use a new user material reference with `desktop_task_resume`; retain the same task ID, inspect `next` and old file receipts, and do not rerun committed work. If the material version or referenced range changed, compare the current file with prior work and explicitly call `desktop_task_resume(acceptCurrentSources=true)` using the fresh reference to every existing task source. This updates the task baseline, invalidates old participant credentials and pending file results, and preserves completed writes, historical feedback, elapsed budgets and pause state. Old working files remain available for comparison, but only a newly prepared current-version copy can be committed. Previous approvals are historical and need a new review. Never automatically broaden the task object list, revive a stopped task or reset its budget.

Use a fresh request ID for a new command, and the same request ID for an exact retry. If an invitation expires, obtain a fresh invitation through the writer; do not silently mark a missing review as approved. If the user prohibited tests, carry that restriction to all delegated executors.
